# 机器狗端深度相机对接说明

本文档说明在**实机**上启动深度相机节点时，与 `our_depth_rl_quadruped_controller` 的对接要求及推荐配置。

**深度图预处理与训练/Onboard 是否一致**：见同目录下 **《深度图处理对齐说明.md》**。

---

## 一、控制器侧要求（必须满足）

### 1. 话题名称与类型

| 用途     | 话题名（控制器订阅）     | 消息类型              | 说明     |
|----------|--------------------------|------------------------|----------|
| 深度图   | `/rgbd_d435/depth_image` | `sensor_msgs/msg/Image` | **必选** |
| 彩色图   | `/rgbd_d435/image`       | `sensor_msgs/msg/Image` | 可选，仅用于可视化 |

- 控制器**只订阅**上述两个话题；深度用于策略输入，RGB 仅用于发布到 `/rgb_image/processed` 供 RViz 等查看。
- 若深度相机节点使用 **namespace**，请保证最终话题为 `/rgbd_d435/depth_image` 和 `/rgbd_d435/image`（可用 remap 或 namespace 实现）。

### 2. 深度图编码（encoding）

控制器支持两种深度编码，**二选一**即可：

- **`16UC1`**：16 位无符号整数，单位**毫米**。控制器内部会乘 `0.001` 转为米。
- **`32FC1`**：32 位浮点，单位**米**。控制器直接使用。

其他编码（如 `8UC1`）不支持，会打警告并跳过该帧。

### 3. 深度数值范围与单位

- 控制器会按 `config.yaml` 中的 **`max_depth`**（默认 **2.0 m**）做裁剪与归一化。
- 深度值应表示**实际距离**（米或毫米），无效/缺失建议发 **0** 或 **NaN**（控制器会做 patchNaNs 和无效比例检测）。
- 若相机输出单位是毫米，请使用 `16UC1`，控制器会自动转换。

### 4. 分辨率与裁剪/缩放（控制器内部）

- 控制器内部会先按 `config.yaml` 做 **crop**，再 **resize** 到固定尺寸送入深度编码器：
  - 裁剪参数（像素）：`depth_crop_top=60`, `depth_crop_bottom=100`, `depth_crop_left=80`, `depth_crop_right=36`
  - 即从原始图中裁掉：上 60、下 100、左 80、右 36，**剩余区域**再参与后续处理。
- 目标尺寸（与训练一致）：**高 58 × 宽 87**（由 `depth_height` / `depth_width` 决定）。
- 因此原始深度图需满足：**高度 > 160**，**宽度 > 116**（否则裁剪后无有效区域）。推荐原始分辨率至少 **240×320** 或 **480×640**。

## 二、实机推荐：RealSense 节点配置

以 **realsense2_camera** 为例，在机器狗端启动深度相机时，需保证话题和编码符合上面要求。

### 方式 A：launch 里直接启动 RealSense（与控制器同机）

在 `hardware_unitree_sdk2/launch/visualize.launch.py` 中已预留 RealSense 节点，取消注释即可：

```python
return [
    rviz,
    robot_state_publisher,
    realsense_camera,   # 取消注释：在机器狗端启动深度相机
    controller_manager,
    ...
]
```

该节点配置为：

- **namespace**：`rgbd_d435` → 话题为 `/rgbd_d435/depth_image`、`/rgbd_d435/image`
- **remap**：`depth/image_rect_raw` → `depth_image`，`color/image_raw` → `image`
- **enable_depth** / **enable_color**：True

这样无需再改话题名即可与控制器对接。

### 方式 B：机器狗上单独起一个 RealSense launch

若希望在机器狗上**单独**启动深度节点（例如不同机器或不同 launch 组合），可新建一个 launch 文件，例如 `depth_camera.launch.py`：

```python
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        Node(
            package="realsense2_camera",
            executable="realsense2_camera_node",
            namespace="rgbd_d435",
            name="camera",
            parameters=[
                {"enable_color": True},
                {"enable_depth": True},
                # 深度图与训练一致：建议 0~2m，单位由 encoding 决定
                {"depth_module.depth_profile": "640x480x30"},
                {"depth_module.enable_auto_exposure": True},
            ],
            remappings=[
                ("color/image_raw", "image"),
                ("depth/image_rect_raw", "depth_image"),
            ],
        ),
    ])
```

要点：

- **namespace** 为 `rgbd_d435`，**remap** 后话题为 `/rgbd_d435/depth_image` 和 `/rgbd_d435/image`，与控制器一致。
- RealSense 默认深度可为 16UC1（毫米）或 32FC1（米），控制器两种都支持。

### 可选：统一深度到 16UC1（毫米）

若希望与仿真/训练更一致，可把深度输出设为 16 位毫米（RealSense 参数中设置深度流为 16UC1、单位毫米），控制器会按 0.001 转为米并做 `max_depth=2.0` 裁剪。

## 三、config.yaml 中与深度相关的参数

在 `config/extreme_parkour_common/config.yaml` 中，与相机相关的关键项如下（保持与训练/仿真一致即可）：

| 参数                  | 含义                     | 典型值 |
|-----------------------|--------------------------|--------|
| `use_camera`          | 是否启用深度输入         | true   |
| `use_depth_cnn`       | 是否用深度编码器         | true   |
| `depth_width` / `depth_height` | 送入网络的深度图尺寸 | 87, 58 |
| `max_depth`           | 有效深度上限（米）       | 2.0    |
| `depth_crop_*`        | 原始图裁剪（像素）       | 见上文 |
| `depth_update_interval` | 每 N 个控制步更新一次深度 | 5      |

实机部署时一般**无需改**上述值，除非你改了训练时的预处理或网络输入尺寸。

## 四、对接检查清单

1. **话题**：  
   `ros2 topic list` 中能看到 `/rgbd_d435/depth_image`（以及可选的 `/rgbd_d435/image`）。

2. **编码**：  
   `ros2 topic echo /rgbd_d435/depth_image --once` 查看 `encoding` 为 `16UC1` 或 `32FC1`。

3. **分辨率**：  
   深度图 `height > 160`，`width > 116`；推荐 480×640 或 240×320。

4. **控制器**：  
   启动 `our_depth_rl_quadruped_controller` 且 `use_camera: true`、`use_depth_cnn: true` 时，无 “Unsupported depth image encoding” 等警告，且策略能收到有效深度（可结合 `/depth_image/processed` 或日志观察）。

5. **同机/异机**：  
   若深度节点与控制器在不同机器，需保证两者 ROS 2 域/网络互通，且话题名仍为 `/rgbd_d435/depth_image`（可通过 remap 或 bridge 实现）。

## 五、常见报错与处理

### 1. `Frame metadata isn't available! (frame_timestamp_domain = RS2_TIMESTAMP_DOMAIN_SYSTEM_TIME)`

- **含义**：RealSense 驱动拿不到硬件时间戳，退回到系统时间。
- **影响**：一般**无实质影响**，仅时间戳对齐略差；图像和深度仍正常。
- **处理**：可忽略。若介意，可尝试换 USB 口（USB3）、换线缆，或更新固件/驱动。

### 2. RViz：`Message Filter dropping message ... queue is full`（camera_color_optical_frame）

- **含义**：RViz 里用于图像+TF 同步的 Message Filter 队列满了，在**显示端**丢帧。
- **影响**：**不影响策略**。策略在 `ros2_control_node` 的控制器里，有独立的深度订阅与回调；RViz 是另一进程，仅做可视化。
- **处理**：可忽略。若想减少刷屏，可在 RViz 中关闭 **Camera** 显示，或把 **Fixed Frame** 临时改为相机帧（如 `camera_color_optical_frame`）再改回 `base`。

### 3. `bad_alloc caught: std::bad_alloc`（反复出现）

- **含义**：内存分配失败（`std::bad_alloc`），多为内存不足或单次分配过大。
- **常见原因**：
  - **分辨率/帧率过高**：深度 + 彩色同时高分辨率（如 1280×720）时，缓冲与处理占用较多内存。
  - **WSL2 内存不足**：WSL2 默认内存有限，与 ros2_control、控制器、RViz 同跑时易触发。
  - **点云/对齐**：若开启了 `pointcloud.enable` 或 `align_depth.enable`，会额外占用内存。
- **建议处理**（按顺序尝试）：
  1. **降低分辨率与帧率**：在启动 RealSense 时加上参数，例如：
     - `depth_module.depth_profile: "640x480x15"`（深度 640×480 @ 15 fps）
     - `rgb_camera.color_profile: "640x480x15"`（彩色 640×480 @ 15 fps）
     控制器内部会 crop/resize，原始 640×480 足够。
  2. **关闭点云**：确保 `pointcloud.enable: false`（默认即为 false）。
  3. **WSL2**：在用户目录下建 `.wslconfig`，增加内存后重启 WSL，例如：
     ```ini
     [wsl2]
     memory=8GB
     ```
  4. **先单独跑相机**：先只启动 RealSense 节点，确认不再出现 bad_alloc 后再与 ros2_control 一起启动，以区分是相机本身还是整机内存紧张。

launch 中若使用本文档推荐的**低分辨率参数**（见下节），可减少 bad_alloc 发生概率。

## 六、launch 中推荐的低内存配置（防 bad_alloc）

在 `hardware_unitree_sdk2/launch/visualize.launch.py` 里启用 RealSense 时，建议传入**限分辨率/帧率**参数，减轻内存压力：

```python
realsense_camera = Node(
    package="realsense2_camera",
    executable="realsense2_camera_node",
    namespace="rgbd_d435",
    name="camera",
    output="screen",
    parameters=[
        {
            "enable_color": True,
            "enable_depth": True,
            "depth_module.depth_profile": "640x480x15",
            "rgb_camera.color_profile": "640x480x15",
            "pointcloud.enable": False,
        }
    ],
    remappings=[
        ("color/image_raw", "image"),
        ("depth/image_rect_raw", "depth_image"),
    ],
)
```

若仍出现 bad_alloc，可再改为 `424x240x15` 等更低分辨率试验。

## 七、接触力阈值可视化调试（防摔倒）

实机易摔倒时，多半与 **`foot_force_threshold`** 有关：阈值过高会“提前判离地”，策略误以为脚已抬起；过低会“迟迟判着地”，抬脚判为仍接触。

### 1. 开启调试发布

在 `config/extreme_parkour_common/config.yaml` 中已默认：

- `publish_foot_force_debug: true`
- `foot_force_debug_topic: "/our_depth_rl/foot_force_debug"`

控制器会以控制频率发布 **Float32MultiArray**，共 5 个数：**[FL, FR, RL, RR, threshold]**（单位 N）。

### 2. 实时绘图（推荐）

先启动实机 launch，再另开终端任选一种方式：

```bash
# 方式 A：ros2 run（需先 colcon build 且脚本已安装到 install/lib/...）
source install/setup.bash
ros2 run our_depth_rl_quadruped_controller plot_foot_force_threshold.py
```

若出现 **No executable found**，先执行 `colcon build --packages-select our_depth_rl_quadruped_controller` 再试。

**方式 B：直接用 Python**（在 workspace 根目录且已 `source install/setup.bash`）  
若本机默认 `python3` 是 Anaconda 的 3.11，会报 `ModuleNotFoundError: rclpy._rclpy_pybind11`（ROS 2 Humble 只支持 Python 3.10）。请用**系统 Python 3.10** 或先退出 conda：

```bash
cd ~/Quadruped_ws
source install/setup.bash
# 任选其一：
python3.10 src/quadruped_ros2_control/controllers/our_depth_rl_quadruped_controller/scripts/plot_foot_force_threshold.py
# 或先退出 conda 再用 python3（若此时为 3.10）
conda deactivate
python3 src/quadruped_ros2_control/controllers/our_depth_rl_quadruped_controller/scripts/plot_foot_force_threshold.py
```

会弹出窗口：四条足端力曲线 + 一条阈值水平线。**力在线上方 = 判为接触**。可据此观察：

- 着地时力是否稳定高于阈值；
- 抬脚时力是否很快低于阈值；
- 若着地力刚好在阈值附近抖动，可适当**降低**阈值；若抬脚时力仍高于阈值，可**提高**阈值。

### 3. 用 rqt_plot 看单腿

若已安装 rqt_plot，可订阅 5 个标量。控制器只发布一个 MultiArray，可用一个桥接节点拆成 5 个话题，或直接使用上面的 Python 绘图脚本。

### 4. 调参后

修改 `config/extreme_parkour_common/config.yaml` 中的 `foot_force_threshold`（单位 N），重启控制器或重新 load 配置后再试。

## 八、实机调试建议（抖动/延迟/观测）

以下对应 `config/extreme_parkour_common/config.yaml` 中可调项，用于排查实机抖动、不稳、延迟等问题。

### 1. PD 增益（最直接）

- **降 Kp**：刚度过大易导致抖动。仿真若用 40，真机可先试 35 或 30（约降 10–20%）。
- **提 Kd**：适当增加阻尼可抑制振荡；过大则会放大速度噪声，需与关节速度滤波配合。
- 参数：`rl_kp`、`rl_kd`（12 个数，与关节顺序一致）。

### 2. Action Scale 与动作平滑

- **action_scale**：策略输出会乘该系数。过大时网络微小波动会被放大成大幅指令，易抖动；一般保持与训练一致（如 0.25）。
- **action_filter_alpha**：动作一阶低通 `last = alpha*current + (1-alpha)*last`。实机救急可设 0.7–0.85，会增相位延迟、影响高动态表现，但能明显减抖。

### 3. 控制频率与 Decimation

- 策略若按 50Hz 控制（仿真 200Hz、decimation=4），则**推理+通信总耗时**应小于一个控制步长（如 20ms），否则会读到旧观测、易震荡。
- 配置中 `decimation: 4` 需与训练一致；控制器内 **`control_step_ms`**（如 20.0）与 `robot_control.yaml` 的 **`update_rate`** 共同决定该步长，详见 **《控制步长与延迟说明.md》**。
- 可开 **`log_inference_latency: true`** 在终端观察推理耗时；若配置 **`latency_log_file`**（如 `"/tmp/rl_latency.csv"`），会每步将 `时间戳, 延迟EMA(ms), under_step(1/0)` 追加写入文件，**under_step=1** 表示延迟小于控制步长、满足实时性，便于离线检查。

### 4. 观测噪声（关节速度滤波）

- 真机关节速度反馈噪声大时，会直接被策略放大导致抖动。
- 已支持 **dof_vel_filter_alpha**：`v_filt = alpha*v_raw + (1-alpha)*v_prev`。0=关闭；真机可设 0.2–0.5（视控制频率调整）。
- IMU 角速度若明显毛刺，可考虑在传感器驱动或观测侧做低通（当前未在控制器内实现）。

### 5. Actuator Net / 电机模型

- 若训练时用了执行器网络（Actuator Net），真机电机型号、磨损、发热等与仿真不一致会导致力矩偏差、“打架”感。
- 本控制器为 PD 位置控制，未接 Actuator Net；若你侧有该模块，需保证真机电机特性与训练域随机化范围匹配，或加大 Domain Randomization 后重训。

## 九、用别人 checkpoint 仍抖动：排查顺序

Extreme-Parkour-Onboard 里同一套策略在别人实机能正常跑，你这边直接用其 checkpoint 却抖动大时，可按下面顺序逐项核对（**优先保证与 Onboard/训练完全一致，再考虑真机特有的滤波**）。

### 1. 控制频率（优先对齐）

- Onboard 实机是 **50 Hz 策略、20 ms 步长**（`run_extreme_parkour.py` 里 `duration=0.02`）。
- 若你当前是 25 Hz（decimation=8），先改回 **decimation=4、control_step_ms=20.0**，与 Onboard 一致再试。推理延迟用 `latency_log_file` 看是否经常超 20 ms；若经常超再考虑降频。

### 2. PD 增益（与 Onboard 一致）

- Onboard 训练 config：`stiffness.joint=40`、`damping.joint=1`。
- 建议先设 **rl_kp=40、rl_kd=1**（不要先加大 Kd），和 Onboard 完全一致；若仍抖再试 rl_kd=1.2 或略降 rl_kp。

### 3. 观测对齐（错一点就易抖）

- **default_dof_pos**：与 Onboard `init_state.default_joint_angles` 一致，且顺序为 **controller joints 顺序**（FL, FR, RL, RR），代码里会按 dof_reindex 转成策略顺序。Onboard 默认站姿：FR_hip -0.1, FL_hip 0.1, RR_hip -0.1, RL_hip 0.1，thigh/calf 0.8 或 1.0、-1.5。
- **观测缩放**：lin_vel_scale=2.0、ang_vel_scale=0.25、dof_pos_scale=1.0、dof_vel_scale=0.05，与 Onboard config 的 `obs_scales` 一致。
- **接触**：foot_force_threshold=25（Onboard 里 `foot_force[i] < 25` 判为离地）。若你机足端力偏大/偏小，可用 `plot_foot_force_threshold.py` 看曲线，微调阈值。
- **深度 yaw**：Onboard `turn_obs` 里 depth yaw 会乘 1.5 再写入 proprio[:, 6:8]；本控制器已做同样处理。
- 若有条件，用 **check_observation_alignment.py** 或 **obs_monitor.py** 对一下 proprio 各段数值范围、顺序是否和 Onboard 一致。

### 4. 动作与输出

- **action_scale=0.25**、**clip_actions=1.2**，与 Onboard 一致。
- **dof_reindex / feet_reindex**：ROS 关节顺序与策略顺序（FR, FL, RR, RL）的映射需与训练一致，否则会“腿错位”导致剧烈抖动。

### 5. 命令（command）来源

- Onboard 用遥控器，parkour 时 commands 为 `[0.5, vy, yaw]`（vx 固定 0.5）。你若用键盘/摇杆，需保证命令范围、死区、缩放与训练/Onboard 一致；命令突变或长期为 0 也可能导致策略行为异常、看起来像抖。

### 6. 推理延迟

- 若推理+通信经常大于控制步长（20 ms），会用到旧观测，易震荡。开 **latency_log_file** 看 under_step 比例；若经常 0，先保证 50 Hz 下能跑满再考虑降频。

### 7. 真机特有：噪声与平滑（在 1–6 对齐后再调）

- **dof_vel_filter_alpha**：真机速度噪声大，可设 0.2–0.5（当前 0.3）；再大更平滑但相位滞后增加。
- **action_filter_alpha**：当前 0.5；仍抖可试 0.65–0.75，用相位换稳定。

**小结**：别人 checkpoint 能跑、你这抖，多半是**控制频率、PD、观测顺序/缩放/接触、或命令**里有一项和 Onboard/训练不一致。先 1→2→3→4→5→6 逐项对齐，再动 7。

## 十、行走时未提前抬脚（脚卡到障碍物才抬）

策略应靠**深度/视觉**提前“看到”障碍并抬脚，若变成**脚卡到障碍物才抬**，多半是前瞻信息没生效或不对，可按下面顺序排查。

### 1. 深度是否真的在用（最优先）

- **话题与数据**：确认 `/rgbd_d435/depth_image` 有数据、encoding 为 `16UC1` 或 `32FC1`、单位/范围符合文档要求。若没深度或长期无效，控制器会把 `depth_latent` 置零，策略相当于“盲走”，只能靠接触反应 → 容易脚卡到才抬。
- **是否被跳过**：若深度帧无效（NaN/0 过多等），会打日志 `Depth invalid -> skip depth encoder (depth_latent=zeros)`。若经常出现，说明深度没参与决策。
- **快速自检**：在 RViz 里加一个 Depth 或 PointCloud 显示该话题，边走边看是否有稳定、合理的深度；再对比 `config` 里 `depth_crop_*`、`max_depth` 是否和训练一致。

### 2. 深度预处理与模型是否和训练一致

- **裁剪与分辨率**：`depth_crop_*`、`depth_width`/`depth_height`（如 87×58）需与训练/Onboard 一致，否则编码出的 latent 和训练分布不一致，策略可能“看不到”障碍或反应错位。
- **max_depth**：与训练深度范围一致（如 2.0 m）；过小会把前方裁掉，过大可能把近处障碍压在一个区间里，都会影响提前抬脚。
- **深度编码器**：`depth_cnn_model`（如 `vision_jit.pt`）需与训练时导出的视觉模型一致；用错或版本不对会导致 latent 语义错乱，策略无法正确利用地形。

### 3. 深度更新频率

- **depth_update_interval**（如 5）：表示每 5 个策略步更新一次深度；与 Onboard 的 `visual_update_interval=5` 一致。若你改得过大（如 10），地形更新太慢，快走时可能“看到”障碍时已经来不及抬脚；可先试改为 3 或 4，观察是否更早抬脚（需与训练侧对齐，否则可能影响稳定性）。

### 4. 接触阈值与“反应式”抬脚

- **foot_force_threshold**：过大会导致“着地”判得晚，策略可能更依赖接触才切换相位，表现为脚已经顶到障碍才抬。可结合 `plot_foot_force_threshold.py` 看着地/离地时力与阈值关系；若着地时力远高于阈值，可适当**降低**阈值，使接触更早被识别，但要注意别把噪声判成着地。
- 提前抬脚主要应来自**深度**；接触阈值主要影响相位切换和稳定性，不是替代深度做“提前”决策。

### 5. 命令与速度

- 若前进速度（vx 等）比训练时大很多，步频/步长会变，策略可能来不及根据深度提前抬脚。可先用与训练接近的速度（如 Onboard 的 0.5）试，确认有提前抬脚后再慢慢提速。

### 6. 小结

| 现象           | 优先排查                         |
|----------------|----------------------------------|
| 脚卡到才抬     | 深度是否在用、是否常被 skip      |
| 深度在用仍晚抬 | crop/resolution/max_depth/编码器 |
| 更新太慢       | depth_update_interval 适当减小  |
| 接触判得晚     | foot_force_threshold 略降并看图  |

按上述配置后，机器狗端深度相机即可与当前代码正确配合使用。
