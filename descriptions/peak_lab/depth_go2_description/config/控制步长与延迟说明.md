# 控制步长与推理延迟说明

本文档说明 `our_depth_rl_quadruped_controller` 的**策略控制步长**如何由配置决定，以及**推理延迟**如何记录、如何判断是否满足实时性要求。

---

## 一、控制步长如何计算

策略并非每个 ros2_control 周期都推理，而是每隔 **decimation** 个周期推理一次，因此：

- **控制器周期**：由 `robot_control.yaml` 中本控制器的 **`update_rate`**（单位 Hz）决定，周期 = `1000 / update_rate` ms。
- **策略控制步长**（两次推理之间的时间间隔）：
  \[
  \text{控制步长 (ms)} = \frac{1000 \times \text{decimation}}{\text{update\_rate}}
  \]

**示例**（与 Extreme-Parkour 训练一致）：

| update_rate | decimation | 控制步长 (ms) | 策略频率 |
|-------------|------------|----------------|----------|
| 200 Hz      | 4          | 20 ms          | 50 Hz    |

即：控制器以 200 Hz 运行，每 4 个周期执行一次策略推理，等价于策略以 50 Hz 更新。

**Extreme-Parkour-Onboard 实机部署**（`run_extreme_parkour.py`）中主循环周期为 **`duration = 0.02` 秒**，即 **50 Hz** 推理、控制步长 20 ms，与上表一致（训练 config 中 `sim.dt=0.005`、`control.decimation=4` → 0.005×4=0.02 s）。

---

## 二、配置位置与一致性

1. **`robot_control.yaml`**（本控制器段落）  
   - **`update_rate`**：控制器回调频率，单位 Hz。  
   - 与训练时仿真环境一致时，一般为 **200**。

2. **`extreme_parkour_common/config.yaml`**（或当前使用的 model_folder 下的 config）  
   - **`decimation`**：每 decimation 个控制器周期执行一次策略，需与训练配置一致（如 **4**）。  
   - **`control_step_ms`**：用于和实际推理延迟比较的“名义控制步长”，单位 ms。  
   - 应满足：`control_step_ms = 1000 * decimation / update_rate`。  
   - 例如：`update_rate=200`、`decimation=4` → **`control_step_ms: 20.0`**。

若修改了 `update_rate` 或 `decimation`，需同步修改 **`control_step_ms`**，否则延迟判断会不准确。

---

## 三、推理延迟与“是否小于控制步长”

- **推理+通信总耗时**应小于一个**控制步长**（如 20 ms），否则会用到过旧观测，易导致震荡或不稳。
- 控制器内部会统计**推理总延迟**的 EMA，并与 **`control_step_ms`** 比较，得到 **under_step**：
  - **under_step = 1**：当前 EMA 延迟 < control_step_ms，认为满足实时性。
  - **under_step = 0**：当前 EMA 延迟 ≥ control_step_ms，可能拖步。

**查看方式**：

1. **终端日志**：开启 `log_inference_latency: true` 后，会按 `latency_log_interval_ms` 周期打印一行，包含 `control_step_ms` 和 `under_step=yes/no`。
2. **写入文件**：若配置了 **`latency_log_file`**（见下），每步会将一条记录追加到该文件，便于离线分析。

---

## 四、延迟日志文件（latency_log_file）

在 **`extreme_parkour_common/config.yaml`** 中：

```yaml
control_step_ms: 20.0
latency_log_file: ""   # 留空不写文件；填路径则追加写入
```

- **`latency_log_file`** 为空：不写文件，仅终端 throttle 打印。
- **`latency_log_file`** 为非空路径：每次推理后追加一行 CSV：
  \[
  \texttt{timestamp\_sec},\;\texttt{latency\_ema\_ms},\;\texttt{under\_step}
  \]
  - `timestamp_sec`：ROS 时间戳（秒）。
  - `latency_ema_ms`：推理总延迟的 EMA（毫秒）。
  - `under_step`：1 表示小于控制步长，0 表示大于等于控制步长。

**示例**：`latency_log_file: "/tmp/rl_latency.csv"`，则可用下列命令做简单统计：

```bash
# 总步数、小于步长的比例
awk -F',' '{c++; u+=$3} END {print "steps:", c, "under_step_ratio:", u/c}' /tmp/rl_latency.csv
```

便于确认实机推理是否大部分时间在控制步长以内。

## 五、小结

| 项目           | 配置项              | 说明 |
|----------------|---------------------|------|
| 控制器频率     | `update_rate`       | robot_control.yaml，如 200 Hz |
| 抽帧倍数       | `decimation`        | 策略 config，如 4，需与训练一致 |
| 名义控制步长   | `control_step_ms`   | 策略 config，20.0 = 1000×4/200 |
| 延迟是否达标   | under_step          | 由 EMA 延迟与 control_step_ms 比较得到 |
| 延迟记录到文件 | `latency_log_file`  | 非空则追加 timestamp_sec, latency_ema_ms, under_step |

控制步长可在**不改变训练**的前提下，通过 **`update_rate`** 与 **`decimation`** 调整；调整后请同步修改 **`control_step_ms`**，并视需开启 **`latency_log_file`** 做离线检查。

---

## 六、推理“慢一点”的配置（实机推理跟不上时）

若实机推理+通信经常超过 20 ms，可**故意降低策略频率**，从而放宽单步允许的耗时（控制步长变长）：

| 策略频率 | 控制步长 | 建议配置（二选一） | 说明 |
|----------|----------|--------------------|------|
| 50 Hz（与训练一致） | 20 ms | update_rate=200, decimation=4, control_step_ms=20 | 默认，与 Extreme-Parkour-Onboard 一致 |
| **25 Hz** | **40 ms** | update_rate=200, **decimation=8**, control_step_ms=**40** | 推理需在 40 ms 内完成即可 |
| 25 Hz | 40 ms | **update_rate=100**, decimation=4, control_step_ms=40 | 控制器整体降为 100 Hz |

**注意**：降低策略频率会与训练时的 50 Hz 时序不一致，可能影响高动态表现；仅建议在实机延迟确实达不到 20 ms 时作为折中。

---

## 七、观测频率与训练是否一致的检验

观测（策略）更新频率需与训练一致（训练为 `sim.dt * decimation = 0.02 s`，即 50 Hz / 20 ms），否则历史观测的时间跨度会错位。

**检验方法**：

1. 在策略 config 中开启 **`publish_obs_freq_debug: true`**。
2. 控制器会向 **`/our_depth_rl/obs_freq_debug`** 发布 `Float32MultiArray`，共 2 个数：
   - `data[0]`：**实际**两次 runModel 之间的时间间隔（ms）
   - `data[1]`：**期望**步长（ms），即 `control_step_ms`（与训练 20 ms 一致）
3. 用 `ros2 topic echo /our_depth_rl/obs_freq_debug` 或 rqt_plot 查看：**data[0] 应稳定接近 data[1]**（如约 20 ms）。若 data[0] 明显大于 20 ms，说明实际策略频率低于训练，需检查 `update_rate`、`decimation` 或 RL 线程是否按预期执行。
